# DXF export integrity

The R2000 writer previously omitted AcDbPolyline (and LINE/TEXT subclass markers).
A synthetic converted polyline reproduced a strict ezdxf DXFStructureError:
`missing AcDbPolyline subclass in LWPOLYLINE`. Tables also lacked subclass markers
and handles. All supported records now carry the appropriate R2000 subclasses
and unique handles. Calibration retains very small nonzero coordinates.

Both single and ZIP exports use buildDxf, which rejects malformed input, non-finite
transformed numbers and empty exports, then checks group pairs, section closure,
entity subclasses and polyline vertex counts before returning download content.
This browser check is intentionally limited; it is not a complete CAD certification.
ZIP filenames are unique case-insensitively, including QA sidecars, and each manifest
entry includes the integrity result. Any invalid sheet aborts the ZIP download.

Validation:
- npm test: 100 tests pass, including actual selected/ZIP handler execution with
  mocked browser download and ZIP interfaces, collisions and blocked downloads.
- python -m pip install ezdxf==1.4.5
- python tests/validate-dxf.py: strict readfile and audit of synthetic raster tracing,
  polyline, dashed/hidden lines, text, circle, solid hatch and crosshatch: eight
  entities, zero audit errors, zero audit repairs. Checks units and coordinates.
- CI runs both suites. No private drawings are fixtures or uploaded.

The original online viewer was not identified and has not been tested directly.
The independent parser reproduces the structural failure and accepts the correction.

## Civil 3D TABLE ordering regression

Civil 3D 2026 reported "Expected dxf code 2, received 5" at line 26.
The generic handle injection placed code 5 immediately after 0/TABLE, ahead
of 2/table-name. Autodesk requires 0/TABLE, 2/name, 5/handle, 100/AcDbSymbolTable,
70/count. ezdxf accepted the malformed order without audit repairs, so an audit
alone was insufficient. Handle injection now treats TABLE headers separately;
pre-download validation and both Node/Python tests enforce the raw header order.
The browser single/ZIP handlers are tested to block this exact malformed output.

Validation: 107 Node tests pass; ezdxf strict load/audit still reports eight
synthetic entities, zero errors and zero repairs. Civil 3D itself was not available
for an application-level reopen test. Previously downloaded files must be
re-exported with the corrected writer.

## Complete R2000 drawing structure

A subsequent Civil 3D APPID error exposed a broader omission: only LTYPE and
LAYER tables were present, and TABLES ended before any APPID table. An ezdxf
read/audit can synthesize required records, so its clean audit did not establish
that the serialized file contained a complete drawing database.

The browser writer now inserts its generated layer/linetype records and modelspace
entities into an empty R2000 scaffold generated by ezdxf 1.4.5. The scaffold contains
VPORT, LTYPE (BYBLOCK/BYLAYER/CONTINUOUS), layer 0, STANDARD text and dimension styles,
VIEW, UCS, APPID/ACAD, model/paper block records and block definitions, linked layout
and group dictionaries, CLASSES and OBJECTS sections, and HANDSEED. New records
receive unique handles and explicit owners; HANDSEED advances beyond all records.
No Python or network service is needed for browser export.

Raw-output validation checks required sections, tables and entries, space blocks,
root ACAD_GROUP dictionary, handle uniqueness, ownership references and HANDSEED.
The Python test also checks essential raw records BEFORE ezdxf populates its model.
Synthetic tests cover missing APPID/ACAD and other tables and unresolved owners.
The scaffold contains no user drawing data. Regenerate with the pinned ezdxf version
using `python tests/generate-dxf-template.py`.

110 Node tests pass. The independent fixture still contains eight entities and
has zero audit errors/repairs. Civil 3D application-level reopening must still be
confirmed; a clean parser audit is not a substitute for that check.
